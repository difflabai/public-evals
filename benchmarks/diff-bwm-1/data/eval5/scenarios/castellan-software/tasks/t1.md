# Task 1: Software Needs Assessment & Capability Plan

## Objective

Assess Castellan Grid Consulting's current tooling and workflow pain, then produce a capability plan covering what to build custom vs buy vs configure vs retain, the integration architecture, a three-phase roadmap with cost bands, and the data-migration and adoption risks — grounded strictly in the engagement source pool and compliant with Foundry's Engagement Deliverable Standards.

## Requirements

- Establish the quantified current state: staffing, revenue at stake, current software spend, utilization, tool inventory, and the measurable costs of the two blown deadlines and the compliance near-miss.
- Reconcile conflicting figures across sources before using them — at minimum the PLS-CADD seat need, the PSA subscription cost, the firm utilization rate, the LiDAR data volume, the RATER data history span, and the disputed root cause of the March compliance near-miss (the Drake rating-workbook incident) — and state which source you treated as authoritative and why.
- Define 6-9 capabilities, each classified build, buy, configure, or retain, with candidate products where relevant, integration dependencies, a phase assignment, a cost band, and risk notes. The sourcing mix must reflect the evidence, not any single stakeholder's preference.
- Evaluate the GridVault Suite proposal against actual requirements, explicitly testing its compliance-workflow and pricing claims against the full record.
- Sequence a three-phase roadmap (Phase 1: 0-6 months; Phase 2: 6-18 months; Phase 3: 18-36 months) that respects the Palisade portal/API deadline and Marcus Brill's December 2027 retirement.
- Enumerate data migrations (at minimum: RATER, the PLS-CADD file share, and the LiDAR archive) with records-at-risk and mitigation notes.
- State nonfunctional requirements (versioning/auditability, security posture for hosted systems, storage scale) derived from the sources.
- Comply with every rule in the Foundry Engagement Deliverable Standards (sources/engagement/kickoff/foundry_engagement_standards.md), including currency formatting, source attribution, gate language, and the closing Sources Consulted section.

## Deliverables

**Prose deliverable — filename:** `software_needs_assessment.md`

The written needs assessment and capability plan described above, in Markdown, compliant with the Foundry Engagement Deliverable Standards.

**Structured deliverable — filename:** `capability_plan.json`

capability_plan.json must be valid JSON with exactly these top-level keys: "current_state_findings" — a list of at least 5 strings, each a quantified finding with its source document named inline; "capabilities" — a list of 6-9 objects, each with keys: "capability_id" (string, e.g. "CAP-01"), "name" (string), "pain_points_addressed" (list of strings), "build_or_buy" (exactly one of "build", "buy", "configure", "retain"), "candidate_products" (list of strings; may be empty for build), "integration_dependencies" (list of capability_ids or system names), "phase" (integer 1, 2, or 3), "est_cost_band_usd" (two-element list [lo, hi] of whole-US-dollar amounts, e.g. 250000 — never thousands or "250K"), "risk_notes" (string); "roadmap" — a list of exactly 3 phase objects, each with "phase" (1|2|3), "timeline" (string, e.g. "months 0-6"), "capability_ids" (list), "exit_criteria" (string); "data_migrations" — a list of at least 3 objects, each with "migration_id" (string), "source_system" (string), "target" (string), "records_at_risk" (string), "mitigation" (string); "nonfunctional" — a list of at least 3 strings stating nonfunctional requirements.
